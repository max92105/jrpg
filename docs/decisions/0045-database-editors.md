# 0045. Database editors

Status: accepted
Date: 2026-11-13

## Context
The editor edits maps, tiles, objects, field sprites and quests; shops and enemies are still hand-written JSON. The
developer wants to set up stores, quest NPCs and monsters from the editor for the introduction and the first quest
line, asked whether that belongs in an editor or in code, and how other engines do it. Data already validates every
catalog file with one validator per content type, the editor saves through `ContentWriter` as one undo history over
`CatalogDraft` (ADR 0012, ADR 0014), and the Quests window (decision 394) is the pattern a catalog window follows.
Plan `2026-11-12-shops-and-enemy-database`, decisions 580-591.

## Options
### A. Hand-written forms per catalog, Data's validators as the one rule source (chosen)
- Pros: each window is a plain view model over Core's records, tested headless; the problem line shows the loader's
  own message through `CatalogProblems`, so no editor rule copies a content rule; rows over a Core enum are generated
  from the enum, so a type added to Core appears in the window; a field added to a record costs one property, one
  XAML row and one test.
- Cons: a form per catalog to write and keep; a new field needs the editor touched beside Core, Data and content.

### B. Forms generated by reflection over the records
- Pros: a new field appears for free.
- Cons: every field looks the same (a text box), choices from other catalogs (an item id, a damage type) need
  attributes or a side table anyway, and the result is a property grid, not a tool.

### C. Forms generated from a JSON schema (.NET's `JsonSchemaExporter`)
- Pros: one schema serves the editor and documentation.
- Cons: the schema says shapes, not rules (an item must be priced to be sold); the rules stay in Data and the form
  would still need them; a second description of each record to keep in step.

### D. An external spreadsheet or database tool exporting the JSON
- Pros: strong for balancing many records at once.
- Cons: a second source of truth beside `content/` (ADR 0011), an export step, and no live check against the other
  catalogs.

## Decision
**A.** Each catalog gets a hand-written window (decision 580); its problem line is its own checks for what Data can't
see (a typed id's shape, a picker left empty) and then `CatalogProblems`' message for the whole edited list. A window
removes only the records added in its session, since maps, events, encounters or saves may name a saved one (decision
581); an id is typed while the record is new and fixed once the draft holds it (decision 582); each window applies its
whole session as one `CatalogDraft` step, so a modal window needs no re-check of the draft under it (decision 591). A
file the editor takes over is relaid once through the writer, with a test that the catalog loaded before and after is
the same, and then the identical-bytes test covers it. The first balancing tool beyond the forms is a read-only
side-by-side table over the draft's records, not more per-record forms.

## Consequences
- **Easier:** a store, a quest NPC or a monster is set up without opening JSON; the editor can't save what the game
  would refuse, and says why in the loader's words.
- **Harder:** the first save of each taken-over file is a large diff with no meaning change (the relay commit); a hand
  edit to such a file while the editor is open is refused at the next save that changes it (decision 559).
- **Watch for:** behavior stays code. What a tactic condition or an effect can do is Core, with its tests; the editor
  only offers the closed list Core defines. New behavior from the editor would mean a scripting layer, which doubles
  the work for one developer and loses the tests.
