# F1. Only whole TrueType fonts reach the rasterizer

Part of [the menu cleanup plan](../README.md). Design: [design.md](../design.md), "What exists" (fonts) and key decision 1.

- **F1. Only whole TrueType fonts reach the rasterizer** (Game, about 150 lines)
  - **Goal:** `FontLibrary.Load` refuses a file that isn't a whole TrueType font. It throws the same `ContentValidationException` (`art/fonts/<file>: not a readable font.`) without handing the bytes to FontStashSharp, and the test host stops dying with 0xC0000005.
  - **Before the fix (diagnosis, in the slice's notes):**
    1. Run `dotnet test --project tests/Jrpg.Game.Tests --filter "FullyQualifiedName~FontLibraryTests"` in a loop (50 runs).
       - A crash or a wrong exception confirms the out-of-bounds read.
       - No crash in 50 runs points to the parallel run instead.
    2. Write down which one it was.
  - **New types (Game):** `Rendering/FontFileHeader`, `internal static`. It answers whether a font file's bytes hold a whole TrueType table directory, with every table inside the file.
    - `public static bool IsComplete(ReadOnlySpan<byte> bytes)`.
    - The format, read big-endian:
      - sfnt version `0x00010000` at offset 0. This is the only kind the content has (one `.ttf`); anything else is refused;
      - `numTables` at offset 4;
      - 16-byte table records from offset 12 (tag, checksum, offset, length).
    - Each record's offset + length must be within `bytes.Length`. Compute it in `long`, so a huge offset can't wrap.
    - The comment cites the OpenType spec ("table directory") and why the check exists: the rasterizer reads through unsafe pointers.
  - **Changes:**
    - `FontLibrary.AddFont` checks `FontFileHeader.IsComplete(bytes)` first and throws the existing message when it's false. The `catch` stays for files that pass the check but still fail in the rasterizer.
    - `FontLibraryTests` gets `[Collection(RepositoryScreenText.CollectionName)]`, so it never builds a `FontSystem` in parallel with the shared one.
  - **Tests (Game):**
    - `FontFileHeaderTests`:
      - `IsComplete_RepositoryFont_ReturnsTrue` (`content/art/fonts/Lato-Regular.ttf`);
      - `IsComplete_ShorterThanTheDirectoryHeader_ReturnsFalse` (the 23 HTML bytes);
      - `IsComplete_OpenTypeCffTag_ReturnsFalse` (`OTTO`);
      - `IsComplete_TableRecordsPastTheEnd_ReturnsFalse` (`numTables` = 10 in a 40-byte file);
      - `IsComplete_TableEndsPastTheFile_ReturnsFalse`;
      - `IsComplete_TableOffsetNearIntMax_ReturnsFalse`.
    - `FontLibraryTests`:
      - the existing `Load_FileThatIsNotAFont_ThrowsNamingTheFile` passes unchanged and no longer reaches the rasterizer;
      - new `Load_TruncatedFont_ThrowsNamingTheFile`: the repository's Lato cut to 1024 bytes, as `cut.ttf`.
  - **Verify by hand:**
    - [ ] Run `dotnet test --project tests/Jrpg.Game.Tests` 20 times in a loop. No host crash, and the same total each run. If it still fails after the header check and the collection, the parallel run was the cause; note it.
    - [ ] Put a truncated copy of `Lato-Regular.ttf` in `content/art/fonts/` and start the game. The startup error names it in the console and the Output window, with no crash. Restore the file afterwards.
    - [ ] Once clean, tell the code reviewer to drop its `flaky-font-test-crash` note.
  - **Diagnosis (before the fix):** the out-of-bounds read. 3 of 50 runs of `FontLibraryTests` alone killed the host ("test session start without end", 1 of 3 tests reported), with no other class sharing the font cache. After the fix: 0 of 50, and 19 of 20 full Game test runs gave 280 tests. The 20th exited with code 127 before any test ran, probably overlapping a concurrent build; it wasn't the crash's signature.
- **Done, with deviations:** one extra test, `IsComplete_TableEndsExactlyAtTheFileEnd_ReturnsTrue` (from the review), pins the `<=` boundary. The two "not a readable font" throws share `NotReadableMessage`.
