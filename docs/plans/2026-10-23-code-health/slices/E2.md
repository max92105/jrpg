# E2. The undo routing leaves `MainViewModel`: `CombinedHistory`

Part of [the code health plan](../README.md). Design: [design.md](../design.md), backlog survey ("`MainViewModel` 596: undo routing"), key decision 5, replacement mapping, risk "E2 touches the XAML bindings"; ADR 0014, decision 117. Comes after E1a.

- **E2. `CombinedHistory`** (Editor, about 300 lines)
  - **Size check at slice start:**
    - Count the members that move (design.md, replacement mapping), the XAML lines, and the test lines that change from `viewModel.UndoCommand` to `viewModel.History!.UndoCommand`: 21 in `MainViewModelUndoTests`, plus any found by Grep in other test classes that go through `MainViewModel`.
    - If the total is over about 300, split before writing code: E2a moves the type and its production callers, with the tests moving in the same commit; E2b covers the XAML and the hand check. Record the split here.
  - **Goal:**
    - The one undo order over the open map and the catalogs is its own type: the journal, the two commands, the refusal and the step wiring.
    - `MainViewModel` loses about 110 lines and keeps only the hand-over of the open map.
    - Behavior is unchanged.
  - **New types:**
    - `Shell/CombinedHistory` (`ObservableObject`, partial for the toolkit): one Undo/Redo over the open map's and the catalogs' histories, in recorded order. It refuses a catalog undo whose removed record is still in use (decision 117).
      - `CombinedHistory(CatalogDraft catalog)`: subscribes to `StepRecorded` and `RedoDropped`.
      - `MapViewModel? OpenMap { set; }`: moves the step subscription, forgets the old map's steps, and refreshes `CanExecute`.
      - `[RelayCommand] Undo()` and `[RelayCommand] Redo()`, generating `UndoCommand` and `RedoCommand`.
      - `string? Refusal { get; private set; }`: was `MainViewModel.UndoRefusal`.
  - **Changes:**
    - `Shell/MainViewModel`:
      - `public CombinedHistory? History { get; }`, created when the content and art loaded (null otherwise, like `Painting`);
      - `OnCurrentMapChanged` sets `History?.OpenMap`;
      - the members in the replacement mapping go.
    - `Shell/MainWindow.xaml`: `UndoCommand`, `RedoCommand` and `UndoRefusal` bind through `History.` (7 places).
    - Tests: `viewModel.UndoCommand`/`RedoCommand` become `viewModel.History!.UndoCommand`/`RedoCommand`, and `viewModel.UndoRefusal` becomes `viewModel.History!.Refusal`. These edits are mechanical, and no other line of the bodies changes. `MapViewModel`'s own `UndoCommand` in other tests stays.
    - `docs/map.md`: the Shell row lists `CombinedHistory` next to `UndoJournal`.
    - `docs/plans/backlog.md`: remove the "`MainViewModel` ... undo routing" line.
  - **Tests:** none new. `MainViewModelUndoTests` and `UndoJournalTests` are the guard.
  - **Verify by hand:**
    - [ ] Paint, mark a tile blocked, then Ctrl+Z twice and Ctrl+Y twice: the same steps in the same order as before.
    - [ ] Edit > Undo, Edit > Redo and the two toolbar buttons work, and grey out when there is nothing to do.
    - [ ] A refused undo (a new object placed on a saved map) shows its message in the status bar; the next edit clears it.
- **Done, with deviations:** size check: about 150 lines for `CombinedHistory`, 120 removed from `MainViewModel`, 7 XAML bindings and 18 test lines, so no split. `OpenMap` has a getter too (a write-only property fails CA1044). `MainViewModel` creates `History` before opening the first map, since `OnCurrentMapChanged` hands the map over; it is 481 lines (was 596). Editor screenshot: Undo and Redo are greyed on open, so the toolbar is bound to the new commands (an unbound button would stay enabled). The three hand checks with edits are left for the developer. Review: no findings; the moved members match line for line apart from the planned renames.
