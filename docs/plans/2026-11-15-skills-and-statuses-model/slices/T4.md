# T4. Every skill names its tiered effect

Content + Data + Game, about 220 lines of code and tests (about 150 of them tests), plus about 40 changed lines of
`skills.json`, one of `enemies.json` and one of `ui.json`. Needs T3 (and row 2's SE2 and SE3, committed before this
plan). Design: design.md, section 3.1 (the table to apply), section 7 (balance).

## Goal
Every skill in `content/skills.json` whose effect is `damage` or `restoreHp` names its tiered effect per design.md,
section 3.1 (`"tier": "fire_1"`, `"power": 0`, its kind and damage type as before), and the Goblin Chief has
`"power": 5`. Data refuses a skill's damage or heal effect without a tiered effect, so a new skill can't slip back to a
flat power. The Status page's Power caption says what Power's percent still raises: "attack damage". The game plays
with the new numbers; the simulations still pass.

## Changes
- `content/skills.json`: the 19 effects of section 3.1 get `"tier"` and `"power": 0`; every other field, SE1-SE3's
  `effectFile` lines included, stays; the descriptions of `heal`, `recovery` and `heal_all` lose their HP numbers
  ("Restores HP to one ally.", "Restores its user's HP, then keeps mending them for two turns.", "Restores HP to every
  ally."; decision 793).
- `content/enemies.json`: `goblin_chief` gets `"power": 5` after `"damageType"` (decision 791), in the writer's layout.
- `Data/Skills/SkillCatalogValidator.FindProblem`: a private `FindTierProblem(Effect effect)`: a `damage` or
  `restoreHp` effect names a tiered effect (`"effect.tier is required for a skill's damage or restoreHp effect: its
  amount is its user's Power times the record's perPower (decision 704)."`); a revive or a status-only skill doesn't.
  It sits in `FindProblem`'s `??` chain right after `EffectValidator.FindProblem(skill.Effect)` (so a malformed effect
  names its own field first) and before the sound file; SE1's `OwnEffectStripValidator` still runs after
  `FindProblem` in `Validate`.
- `content/text/ui.json`: `status_power_gives` reads `"{damage} % attack damage"` (decision 793);
  `Game/Ui/MessageIds.StatusPage`'s summary for `StatusPowerGives` says so.
- Repository tests that pinned a skill's power, rewritten to ids and shape (never the new value):
  - `ContentCatalogLoaderTests.Load_RepositoryContent_RecoveryHealsItsUser` (it compares the whole effect with power
    30): assert `RestoreHp`, `Targeting.Self`, a tiered effect, and the Regen grant's kind and turns as before.
  - `Jrpg.Data.Tests/TestContent/skill-without-description.json` keeps failing on its missing description (the
    serializer refuses it before the tier rule); check, no change expected.
- `Data.Tests/Skills/SkillCatalogValidatorTests`: the fixtures `_heal` and `_blast` are rebased to tiered effects (a
  `heal_1` and a `fire_1` record built in the test, `Power: 0`, `Tier` set), so every existing row (the effect file
  rows on `_blast` and `_heal` included) keeps tripping only its own rule; the row `_heal.Effect with { Power = -5 }`
  still reads "effect.power must be at least 0" (`EffectValidator` checks the power first); the revive row keeps its
  flat power.
- `Game.Tests/Menus/AttributeCaptionsTests`: its two expected strings ("+15 % damage", "+0 % damage") read "attack
  damage"; grep `Jrpg.Game.Tests` for "% damage" for any other.
- Game tests on repository skills (`BattleScenarios.Skills`): run `Jrpg.Game.Tests`. Known: `StatusMarksViewTests`
  bashes a 30 HP goblin with Sarxian (Power 12: `blunt_1` deals 24, it survives); `BattleTurnSequenceTests` and
  `ActionWindUpTests` use Shield Bash for its stun. A test failing on a repository skill's amount is moved onto a skill
  built in the test, its reason in the Done note.
- Simulations: build, then run `tests/Jrpg.Simulations/bin/Debug/net10.0/Jrpg.Simulations.exe -showLiveOutput`;
  paste the Chief's table in the Done note. `ForestFightsSimulation` doesn't move (attack only, enemies without
  skills); `BossFightSimulation` asserts that every fight ends, the Chief uses each action and reaches its phase: if
  one fails, the reason goes in the Done note before any re-pin (decision 813).
