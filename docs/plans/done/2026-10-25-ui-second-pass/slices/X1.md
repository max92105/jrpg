# X1. The inn fades to black, holds, then says the party rested

Part of [the UI second pass plan](../README.md). Design: [design.md](../design.md), "Tunables and placeholders" (rest fade), "Key decisions". After C3.

Decision 257: fade to black, hold, "the party rests"; music comes later. The Camp Kit from the menu keeps its message only.

- **X1. The inn fades to black, holds, then says the party rests** (Game, about 170 lines)
  - **Goal:** when a map event reaches a rest step (the inn), the screen fades to black, stays black for a second, fades back, and only then shows the "party rests" message. The classic inn beat, with no new event step.
  - **Changes (Game):**
    - `Exploration/EventPresenter`: a `_restFade` (`ScreenFade`: 0.5 s out, 1.0 s black, 0.5 s in). The rest step's first update starts it; while it plays, the step isn't shown and `IsBusy` is true; `Blackness` takes the larger of the warp fade, the rest fade and the stills; when it ends, the step's page shows as today (`ShowPages`). A rest step whose fade has run doesn't start it again (the page's own updates).
    - When Core applies the rest doesn't change (the step, as today): the map shows no HP, so nothing visible changes before the black.
    - It must stay under 300 lines after C3; if not, the rest timing moves into a small `Exploration/RestFade`.
  - **Tests** (a new `EventPresenterRestTests` class, since `EventPresenterTests` is at 304 lines; it builds the start map's inn event like `StartMapScenarios`):
    - `Update_RestStepStarts_ScreenGoesBlack` (after the fade-out time, `Blackness` is 1)
    - `Update_DuringRestFade_ShowsNoMessage`
    - `Update_AfterRestFade_ShowsThePartyRestsMessage`
    - `IsBusy_DuringRestFade_IsTrue`
  - **Verify by hand:** talk to the innkeeper on the start map: the greeting, then black for about two seconds in all, then "the party rests"; walking resumes after the message. In battle afterwards, everyone's HP and lasting resources are full (as before). The Camp Kit from the menu shows its message as before.
- **Done, with deviations:**
  - **Where the fade lives:** in `EventPresenter`, which is now 238 lines, so no `RestFade` type was needed. `IsBusy` needed no change, since the event runs for the whole fade.
  - **Tests:**
    - `IsShowingMessage` (internal, like `IsShowingStill`) lets the tests see the message.
    - The existing `Update_RestStep_ShowsRestLineThenContinues` gains one update that plays the fade first; `EventPresenterTests` grows from 304 to 305 lines (already in the backlog).
    - 5 new tests (2118 in all); after review, `Update_SecondRest_FadesAgain`, which fails without the flag's reset.
